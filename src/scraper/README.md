# 采集端（Playwright）

采集端用 Playwright 实际操作页面：登录、填日期筛选、滚动列表、点进明细、核对数据、返回列表，全程只读取页面上可见的内容。
不读取 `window.__SITE_BOOT__`，不调用 `/api/**`；运行器还注册了 `page.route('**/api/**')` 拦截，页面若尝试访问内部接口会被 abort 并记一条 `API_ACCESS_BLOCKED` 警告。

## 列表：虚拟滚动下如何采全

演示站点的列表使用**虚拟滚动**：页面上只挂可视区域内的十几行（固定行高 56px、视口 560px、overscan 2），其余行靠滚动位置计算。
因此采集器不逐页点击，而是：

1. 先打开带筛选参数的列表（首次运行还会在页面上真实填写日期并点「筛选」）；
2. 把滚动位置从当前位置扫到底，再回绕覆盖起点之前的部分，每个位置都读取**与视口真正相交**的行（`getBoundingClientRect` 与视口比较）；
3. 行节点会被复用，所以一律按 `orderNo` 去重，同一订单号只记录第一次被看到时的滚动位置；
4. 每扫到一屏就把新行增量落库（`orders` 表），进度写入 `batches.progress_json`，进程中断后可从保存的位置续采；
5. 列表采集的完成条件是「页面滚到底并渲染出『已滚动到底部』提示」**且**「本批快照内的已收集数 == 建批时冻结的筛选总数」。
   数量对不上就不算完成：运行以 `incomplete` 结束，而不是伪造结果。

## 快照固定

批次建立时冻结 `snapshotMaxPlacedAtMs` 与站点 `dataVersion`。采集时 `placedAtMs` 晚于快照的订单会被排除，并记 `NEW_ORDERS_EXCLUDED` 警告；
若页面数据版本与批次固定值不同，再记 `DATA_VERSION_CHANGED` / `DATA_VERSION_DRIFT`。因此批次运行期间新建的订单不会混进这一批。

## 明细与校验

- 点进明细前，把筛选条件、排序口径、当前滚动位置、当前订单号写入进度。
- 只通过点击页面上真实存在的行链接进入明细（`openOrderDetail` 会先确认该行确实处于可视区域，找不到就报错，不会构造 URL）。
- 等 `#detail-card[data-detail-ready="ready"]` 出现（延迟开关生效时页面先显示「正在加载…」），再读订单号、明细行数、单价/数量/行金额/合计。
- 核对项：订单号与列表行一致；明细行数 == 页面标注项数 == 列表行标注项数；每行 `单价 × 数量 = 行金额`（整数分运算）；行金额合计 == 明细总额 == 列表总额。买家/下单时间不一致记 warning。
- 每单核对后截图 `#detail-card`；失败额外截 `-failed.png`。截图路径以相对截图根目录的形式入库。
- 返回列表后，页面会从 `sessionStorage` 恢复滚动位置并回写 `data-restored-scroll-top`；采集器核对恢复值与点击时的位置，一致就从那里继续。

## 登录过期

自动退出登录开启后，会话过期会让列表/明细请求返回「登录已过期」页。采集器在列表滚动、明细等待、返回列表这几个环节都会检测该页：

- 一旦检测到立即暂停，把当前进度（已落库订单、滚动位置、当前订单号）写入批次并记 `LOGIN_EXPIRED`；
- 下次运行用页面上的「重新登录」链接与登录表单重新登录（不会用脚本伪造会话）；
- 只处理未完成（`pending`/`failed`）订单，已核对订单不会重采、不重复截图。

## 重复执行

批次 id 由 `sha256(站点地址|开始日期|结束日期)` 前 10 位与筛选范围拼接而成，同一筛选范围重复建批会复用原批次与原进度。
所以「重新运行同一批次」等于「继续这个批次」，而不是新开一批。
